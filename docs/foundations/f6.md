# F6 · 솔루션 킷 = 저장소 하나

6일 동안 만든 것을 **저장소 하나**에 담고, 처음 보는 사람도 README만 보고 **다시 돌릴 수 있게** 만들면 그것이 솔루션 킷입니다. 제출은 **릴리스 `v1.0`** 으로 고정합니다.

<small>[이론 요약 2장](../day6/theory.md#ch2)을 보충하는 짧은 해설</small>

</div>

## 1. 비유 — 밀키트 {#analogy}

- **솔루션 킷 = 밀키트.** 재료(`data/`) · 조리 도구(`app/`) · 위기 때의 순서(`sop/`) · 가격표(`roi/`) · 설명서(`docs/`)를 한 상자에 담고,
  상자 겉면에 **조리법(README)** 을 붙입니다. 누가 받아도 같은 요리가 나와야 합니다.
- **README = 상자 겉면의 조리법.** 어떤 파일로 · 무엇을 누르면 · 무엇이 나오는가(재현 절차).
- **이슈 = 할 일 쪽지, PR = 완성한 조각을 합치자는 요청.** 역할마다 이슈를 하나씩 맡고, 끝낸 조각은 PR로 합칩니다.
- **릴리스 `v1.0` = 봉인 테이프.** 제출 시점의 상자를 그대로 고정합니다(중간 점검은 `v0.5`).
- **스트레스 테스트 = 일부러 세게 흔들어 보기.** 극단적인 위기 카드로 파이프라인 전체를 돌려 **어디가 먼저 깨지는지** 찾습니다.

## 3. 용어 {#terms}

| 용어 | 한 줄 정의 |
|---|---|
| **README · 릴리스(태그)** | 저장소 첫 화면의 사용설명서 · 특정 시점의 저장소에 이름(v1.0)을 붙여 고정한 배포본 |
| **스트레스 테스트 · 위기 카드** | 극단 시나리오로 전체를 돌려 약한 곳 찾기 · 가상 위기 카드를 받아 역할을 나눠 실제처럼 대응하는 훈련 → [용어집 6일차](../glossary.md#day6) |
| **거버넌스 · AI 사용 규칙서** | 누가 무엇을 결정·승인·기록하는지 정한 체계 · 넣으면 안 되는 데이터, 반드시 할 검증, 기록 방식을 적은 팀 규칙 |

알아 둘 것

- **README 5항목**: 목적 · 구성 · 실행 방법(재현 절차) · 데이터 원천과 가상 여부 · 담당자.
- **폴더 구조**는 [솔루션 킷 안내](../day6/kit.md#structure)에 있습니다. 팀 저장소는 5일차 8교시에 킷 템플릿으로 이미 만들어 두었습니다(비공개 · 팀원과 강사는 협업자).
- **운영 보안 점검**: 키를 지우거나 교체했나 · 저장소에 실데이터가 0건인가 · 협업자 권한이 맞나 · AI 사용 규칙서가 있나.

## 5. 익명 실패 사례 {#case}

<span class="chip chip--field">[현장 사례 · 익명]</span> **"문서와 코드가 다르다"**

README에 적힌 모델 이름이 실제 코드와 달랐고, README가 실제 구현보다 많은 기능을 주장한 경우도 있었습니다.
짧은 요구 문서에 적힌 필터 하나는 끝내 화면에 연결되지 않았습니다.

**교훈** — AI가 쓴 문서도 검증 대상입니다. 제출 전에 **팀 밖의 한 사람이 README만 보고 5분 안에 재현**해 봅니다(심사 기준 ③ 솔루션 킷 품질).
