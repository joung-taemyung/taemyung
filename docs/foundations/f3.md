# F3 · 같은 입력이면 같은 결과

분석 결과는 **다시 돌려서 같은 숫자가 나와야** 믿을 수 있습니다. **코드 · 데이터 · 환경 · 시드** 네 가지를 고정하고 기록해 두면 '어제는 됐는데 오늘은 안 되는' 일이 줄어듭니다.

</div>

## 1. 비유 — 레시피 카드와 같은 상표의 재료 {#analogy}

- **코드 = 레시피.** 순서가 한 줄만 달라도 맛이 달라집니다. Git 커밋 해시가 '어느 판의 레시피로 만들었나'를 가리킵니다.
- **데이터 = 재료.** 재료가 바뀌면 같은 레시피도 다른 음식이 됩니다. 파일의 해시(sha256)가 '같은 재료인가'를 확인해 줍니다.
- **환경 = 같은 상표의 재료와 같은 주방.** 프로그램(패키지) 버전이 바뀌면 같은 레시피도 맛이 조금 달라집니다. 이 저장소에서는 `uv.lock`이 버전을 그대로 고정합니다.
- **시드 = 주사위를 같은 순서로 굴리게 하는 번호.** 데이터를 무작위로 나누거나 섞을 때 시드(`random_state = 42`)를 고정하면 매번 같은 결과가 나옵니다.

## 2. 그림 — 폴더에 남는 것 {#figure}

2일차의 프로젝트 구조(`data/` `src/` `tests/` `CLAUDE.md` `uv.lock`)에 3일차의 ML이 더하는 것은 다음과 같습니다.

```text
+ params.yaml          # 하이퍼파라미터 · 비용비
+ src/train.py · score.py · evaluate.py
+ models/day3_lgbm.txt      # 학습된 모델(day3_lgbm_v1)
+ models/model_card.md      # 모델의 이력서
+ models/metrics.json       # PR에서 비교할 지표
+ .github/workflows/train.yml
$ uv run python src/train.py --params params.yaml
```

## 3. 용어 {#terms}

| 용어 | 한 줄 정의 |
|---|---|
| 용어 3-35 **재현성 · 시드 · 버전 고정** | 같은 입력 · 같은 절차면 같은 결과가 나오는 성질 · 무작위 과정을 고정하는 번호(`random_state`) · 쓴 프로그램 버전을 정해 두고 기록하기 |
| 용어 3-13 **실험 추적** | 실행마다 설정 · 지표 · 산출물 · 코드 커밋을 자동으로 남겨 비교하는 일(예: MLflow) |
| 용어 3-14 **모델 카드** | 모델의 목적 · 데이터 · 성능 · 임계값 근거 · 한계를 적은 한 장 |

알아 둘 것

- **네 중 하나만 바뀌어도 숫자가 바뀝니다.** 월요일에 다시 돌린 등급이 금요일과 다르면 한도 결정의 근거가 흔들립니다. 한 연구에서 GitHub의 노트북 86만여 건을 다시 실행했더니 오류 없이 돈 것이 24%, 같은 결과를 낸 것은 4%뿐이었습니다.
- **시드는 무작위가 쓰이는 모든 곳에.** 학습 · 시험 분할, 모델 학습, SMOTE, 부트스트랩이 각각 시드를 가집니다. 하나만 고정하면 나머지에서 숫자가 흔들립니다.
- **패키지 버전은 `uv.lock`에 맡기고, 결과 옆에 한 줄 적습니다.** `uv run python -c "import lightgbm, sklearn; print(lightgbm.__version__, sklearn.__version__)"`로 찍은 버전을 `notes.md`에 남깁니다.
- **AI가 코드를 고르면 숫자도 달라집니다.** 같은 프롬프트라도 AI가 고른 특성 구성이 다르면 소수 셋째 자리가 달라집니다(오전 시연 3의 63열 대 42열). 그래서 **분할 · 특성 · 설정을 프롬프트에 문장으로 적어 줍니다** — 오늘 A2 프롬프트가 LightGBM의 설정과 시드를 적어 주는 이유입니다.
- **노트북으로 한다면** VS Code 노트북의 커널은 `.venv`이고, 마무리는 **'커널 재시작 후 모두 실행'**으로 맨 위부터 다시 돌려 같은 숫자가 나오는지 봅니다. 중간 칸만 여러 번 돌린 결과는 재현되지 않을 수 있습니다.
- **이해의 부채**: AI가 만든 코드 · 결과를 내가 설명할 수 없으면 제출하지 않습니다.

## 5. 현장 이야기 — "설명할 수 없으면 커밋하지 않는다" {#case}

AI 코딩 도구를 쓰면서 개발 속도가 크게 빨라지자, 만든 사람도 설명하지 못하는 코드와 결과가 쌓이기 시작한 팀이 있었습니다.
돌아가기는 하는데 왜 그 숫자가 나오는지, 어디를 고쳐야 하는지 답하지 못하는 상태 — **이해의 부채**입니다.
그 팀은 "설명할 수 없으면 커밋하지 않는다"를 규칙으로 정하고, 제출 전에 짧은 이해도 점검으로 스스로 확인합니다.

**교훈** — 재현성은 두 가지입니다. **다시 돌리면 같은 숫자**, 그리고 **그 숫자를 설명할 수 있음**.
