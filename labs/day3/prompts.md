## 프롬프트를 쓰는 습관 {#habits}

1. **정의와 결정은 문장으로 준다** — 무엇이 정답(`late_30d`)인지, 어디서 나눌지(`split_suggested`), 비용비가 얼마인지는 사람이 정해 프롬프트에 적습니다. 그 문장이 곧 좋은 프롬프트입니다.
2. **계획을 먼저 읽는다** — Plan 모드의 계획에서 금지 열 표 · 분할 · 만들어질 파일 이름을 확인한 뒤 승인합니다.
3. **숫자는 코드가, 확인은 손으로** — 계산은 스크립트가 하고, 나는 한 줄이라도 직접 대조합니다(비용표 한 줄 · 완성본 엑셀).
4. **틀리면 바로 고치게 하지 않는다** — "어느 쪽이 틀렸나"를 먼저 묻습니다([안 맞을 때](#mismatch)).
5. **허락 창은 읽고 승인한다** — 무엇을 · 어디에 · 지우는지 세 가지를 읽고 `1 Yes`. 파일 삭제 · 강제 push · `git reset --hard`는 거절합니다.
6. **AI 초안은 내 말로 고친다** — 근거 메모의 결론 · 확인할 것 · 한계는 AI가 쓴 그대로 두지 않습니다. 마지막 줄 '사람 승인 전 초안'이 그 약속입니다.

## A2 · 첫 모델 — 로지스틱과 LightGBM {#a2}

**도구** Claude Code · **모드 Edit automatically(또는 Manual)** · **실습 A-1 · 03** · 결과 `d3_train.py` · `d3_eval.md` · `d3_test_pred.csv` · `model_v1.txt`

<!-- --8<-- [start:a2] -->
```text
workbench/day3/outputs/d3_train.py를 만들어 실행해.
① split_suggested로 학습/시험
② 특성: 데이터 카드의 '특성' 열만(sample_weight · split_suggested · buyer_id · ref_date 제외). 문자 열은 payment_method만 원-핫으로 쓰고 나머지 문자 열은 빼
③ 모델: 로지스틱 회귀(결측 중앙값 · 표준화)와 LightGBM(random_state=42 · n_estimators=300 · learning_rate=0.03 · num_leaves=7 · min_child_samples=10 · subsample=0.8 · subsample_freq=1 · colsample_bytree=0.8 · reg_lambda=5 — 오전 슬라이드의 학습 코드와 같은 설정에서 학습 연체가 12건뿐이라 min_child_samples만 30 → 10)
④ 시험셋 ROC-AUC · PR-AUC · Brier와 임계값 0.5 혼동행렬
⑤ 결과는 d3_eval.md 표로, LightGBM의 시험셋 예측은 d3_test_pred.csv(buyer_id · ref_date · late_30d · pd_30d)로, LightGBM 모델은 model_v1.txt로 저장. 패키지 버전도 출력해.
```
<!-- --8<-- [end:a2] -->

**어떻게 생겼나** 오전 시연 3을 **300행 · 모델 2개 · 이미 나뉜 `split_suggested`**로 줄인 것입니다. 학습 212행(연체 12건) · 시험 88행(연체 4건)이고, 시험셋은 마지막 성적표라 한 번만 봅니다. LightGBM의 **하이퍼파라미터(학습 전에 사람이 정하는 설정값)를 프롬프트에 적어 준** 이유는 둘입니다 — 같은 문장이면 사람마다 비슷한 숫자가 나오게 하려는 것, 그리고 슬라이드의 `min_child_samples=30`(또는 기본값 20)이면 연체 12건을 잎으로 떼어 내지 못해 확률이 몇 가지 값으로만 나오고 비용표가 평평해지기 때문입니다. 다른 줄은 오전 슬라이드의 학습 코드 그대로입니다.

**확인할 것**

- 시험셋이 **88행 · 연체 4건**인지 봅니다. 아니면 `split_suggested` 값 `train` / `test`를 쓰는지 확인합니다.
- ROC-AUC는 **0.80–1.00** 사이에서 사람마다 다른 것이 정상입니다(로지스틱은 대개 0.80–0.90, LightGBM은 0.93–0.97) — 시험 연체가 4건뿐이라 한 건에 크게 흔들립니다. 0.99 이상으로 붙어 있으면 누수부터 의심합니다.
- `d3_train.py`가 **원본 CSV를 덮어쓰지 않는지**, 특성에서 `sample_weight` · `split_suggested`가 빠졌는지 훑어봅니다.

## A3 · 누수 실험 — sample_weight를 넣으면 {#a3}

**도구** Claude Code · **실습 A-1 · 04** · 결과 `d3_eval.md`에 3줄 추가 + 코드 원상복구

<!-- --8<-- [start:a3] -->
```text
먼저 git add workbench/day3/outputs/d3_train.py 로 지금 코드를 스테이징해 둬(원래 모습의 기준이 된다).
그다음 같은 코드 · 같은 설정으로 sample_weight를 특성에 더해 로지스틱 회귀와 LightGBM을 한 번씩만 돌려 AUC를 비교해. 실험 때는 d3_test_pred.csv · model_v1.txt를 덮어쓰지 마(실습 B가 쓴다).
왜 AUC가 1.0에 가까워지는지 3줄로 d3_eval.md에 추가하고, 실험이 끝나면 코드를 원래대로(sample_weight 제외) 돌려 놓은 뒤 git diff가 비어 있는지 보여 줘.
```
<!-- --8<-- [end:a3] -->

**어떻게 생겼나** `sample_weight`는 **정답으로 계산한 가중치**입니다 — 연체 행은 9.375, 정상 행은 0.528 두 값뿐입니다. 이 열 하나로 정답을 읽을 수 있어 AUC가 **1.00**으로 뛰어오릅니다(오전의 AUC 1.0 연체 모델과 같은 일). 누수는 이렇게 **너무 좋은 숫자**로 드러납니다.

**확인할 것**

- 두 모델 모두 AUC가 **1.00 근처**로 오르는지 봅니다(A2의 설정 그대로면 로지스틱도 LightGBM도 1.000이 나옵니다).
- **LightGBM이 안 오른다면** 열이 빠진 것이 아니라 설정 때문일 수 있습니다. 학습셋의 연체가 12건뿐인데 기본값은 '잎 하나에 최소 20행'이라, 그 12건을 따로 떼어 낼 수 없습니다. 그래서 A2에서 `min_child_samples`를 슬라이드의 30에서 10으로 낮춰 두었습니다. 20이나 30으로 돌리면 `sample_weight`를 넣어도 AUC가 그대로인 것을 볼 수 있습니다 — 작은 표에서는 모델 설정이 누수를 가리기도 합니다.
- 마지막 `git diff`가 **비어 있는지** 확인합니다. 실험 전에 `git add`로 코드를 스테이징해 둔 것이 '원래 모습'의 기준이라, 실험 때 바꾼 줄이 남아 있으면 `git diff`에 보입니다(`sample_weight`가 다시 빠졌는지).
- 결과 파일 `d3_test_pred.csv` · `model_v1.txt`는 아직 커밋 전이라 `git diff`가 지켜 주지 않습니다. 프롬프트의 '덮어쓰지 마'가 그 몫입니다 — 누수 모델로 덮어썼다면(A4 비용표가 FN 0 · FP 0으로 완벽하게 나온다) `uv run python workbench/day3/outputs/d3_train.py`를 한 번 더 돌려 되돌리고, 누수 3줄은 다시 붙여 달라고 합니다(이 스크립트가 `d3_eval.md`를 새로 쓰기 때문).

```text
시험셋 예측(d3_test_pred.csv)으로 임계값 0.05~0.50(0.05 간격) 표를 만들어: TP · FN · FP · TN · 재현율 · 정밀도 · 경보 수 · 비용(5×FN + FP).
최소 비용 t와 이론값 1/6(≈ 0.17)을 비교하고, 최소 비용 t와 t = 0.17 두 곳에서 놓친 바이어(FN)의 buyer_id · ref_date · pd_30d와 주요 특성 3개(값 포함)를 표로.
workbench/day3/outputs/d3_threshold.md로 저장해.
```
<!-- --8<-- [end:a4] -->

**어떻게 생겼나** 오전 시연 4(엑셀 시뮬레이터)를 **Markdown 표**로 줄인 것입니다. 비용 5 × FN + FP는 "놓친 연체 1건 = 헛경보 5건"이라는 사내 가정이고, 이론상 최적 임계값은 t = 1 ÷ (1 + 5) ≈ **0.17**입니다. 놓친 바이어를 **두 곳(최소 비용 t와 0.17)**에서 보는 이유는, 시험 연체가 4건뿐이라 최소 비용 t에서는 놓친 바이어가 1곳뿐이어서 공통점을 찾을 수 없는 경우가 많기 때문입니다.

**확인할 것**

- 표가 `0.05, 0.10, … 0.50` 열 개 줄이고 비용 열이 `5 × FN + FP`와 같은지 **한 줄을 손으로** 계산해 봅니다(예: t = 0.50 줄의 FN과 FP로).
- 최소 비용 t가 이론값 0.17과 **다르게 나와도 정상입니다.** 시험 연체가 4건뿐이라 비용이 계단처럼 움직이고(한 칸이 연체 1건), 표 전체가 몇 줄씩 같은 값일 수 있습니다. 최소 비용 t는 이 설정이면 0.10–0.25 근처가 나오는 사람이 많지만, 시드 · 특성 · 설정에 따라 0.05나 0.30 이상이 나오기도 합니다. 차이를 **한 줄로** 적는 것이 오늘의 연습입니다.
- 놓친 바이어(FN)의 특성 세 개를 나란히 보고, 모델이 무엇을 못 보는지 오전 '한계' 장의 내용과 맞는지 생각해 봅니다(공통점 2줄). 주요 특성은 연체 · 잔액 관련 열(`oldest_open_days` · `max_dpd_180d` · `pct_current` · `overdue_amount_usd`)이 읽기 쉽습니다.

**내 회사 비용비로 다시** — 놓친 연체가 내 회사에서는 헛경보 몇 건만큼 아픈지 정해 한 번 더 돌립니다. 3:1이면 t = 0.25, 10:1이면 t ≈ 0.09입니다([빈칸 값](#values)).

<!-- --8<-- [start:a4-cost] -->
```text
내 회사 비용비 {FN비용}:1로 같은 표를 다시 만들어 d3_threshold.md에 이어서 써 줘. 이론 t = 1 ÷ (1 + {FN비용}), 최소 비용 t, 경보 수, 놓친 연체 수를 5:1일 때와 나란히 놓고, 무엇이 바뀌었는지 1줄로 정리해.
```
<!-- --8<-- [end:a4-cost] -->

3:1인데 표의 최소 비용 t가 5:1과 같게 나오는 일이 흔합니다(같은 계단) — 그때는 **이론 t와 그 t에서의 경보 수** 쪽 변화를 씁니다. 10:1의 이론 t 0.09는 0.05 간격 표에 없으니 "이론 t 행을 한 줄 더해 줘"라고 덧붙여도 됩니다.
